# 내가 만든 부분: 골격 맞춤 추천 (C 파트) 쉬운 설명

## 한 줄 요약
"이 사람 체형에는 어떤 옷이 어울리는지"를 점수로 계산해서, 쇼핑 앱 홈 화면처럼 **추천 목록, 코디, 추천 이유**를 보여 주는 부분을 만들었어요.

## 비유로 이해하기: 옷가게 점원
옷가게에 센스 있는 점원이 있다고 생각해 보세요. 손님이 들어오면 점원은 이렇게 일해요.

| 점원이 하는 일 | 우리 프로그램에서는 | 담당 |
|---|---|---|
| 손님 체형을 본다 ("어깨가 반듯하시네요") | 설문·아바타로 골격 타입을 판정 | A 파트 |
| 옷마다 이 손님에게 어울리는지 따진다 | 옷 하나하나에 "체형 적합도" 점수 | B 파트 |
| **어울리는 옷을 골라 순서대로 보여 준다** | **최종 점수 → 순위 → 홈 화면** | **C 파트 (나)** |
| **"이 셔츠에 이 바지 어때요?" 코디를 제안한다** | **상의+하의 조합 추천** | **C 파트 (나)** |
| **"칼라가 목선을 살려 줘서요" 이유를 말한다** | **추천 이유 문장** | **C 파트 (나)** |
| **손님 반응을 기억해 다음에 더 잘 고른다** | **클릭·찜·구매로 취향 학습** | **C 파트 (나)** |

즉 C 파트는 점원이 **최종적으로 무엇을, 어떤 순서로, 왜 보여 줄지** 정하는 역할이에요.

## 먼저 알아야 할 것: 골격 3타입
- **스트레이트**: 몸이 직선적이고 탄탄함 → 셔츠, 일자 바지처럼 깔끔한 옷이 어울림
- **웨이브**: 곡선적이고 부드러움 → 크롭 니트, 하이웨이스트처럼 허리를 살리는 옷이 어울림
- **내추럴**: 뼈대가 크고 시원함 → 오버사이즈, 와이드처럼 여유 있는 옷이 어울림

사람은 딱 한 타입이 아닐 수 있어서 "스트레이트 60%, 웨이브 30%, 내추럴 10%"처럼 **비율**로 표현해요.
1등 타입이 2등보다 10%p 이상 높으면 **단일형**, 아니면 **혼합형**이에요.

## 내가 만든 7단계

### 1단계: 연습용 상품 30개 + 규칙표
진짜 쇼핑몰 데이터가 아직 없어서 연습용 옷 30개를 만들었어요.
옷마다 "칼라 있음", "몸에 맞는 핏", "탄탄한 소재" 같은 **꼬리표(태그)**를 붙였어요.
그리고 스타일 가이드를 표로 바꿨어요. 예: 스트레이트에게 "칼라"는 어울림(+2점), "러플"은 피해야 함(−3점).

### 2단계: 최종 점수 계산
옷마다 점수를 매겨요. 시험 점수를 과목별 비중으로 합치는 것과 같아요.
- 체형에 맞는가: **60%**
- 이 사람이 좋아하는 스타일인가: **25%**
- 지금 계절에 맞고 인기 있는가: **15%**

단일형인 사람에게 "피해야 할 옷"은 **아예 추천에서 빼요.** 혼합형이면 빼지 않고 점수만 깎아요.
(예: 확실한 스트레이트에게 러플 블라우스는 안 보여 줌)

### 3단계: 순위 정하기 + 골고루 섞기
점수순으로 줄을 세우되, 상의만 3개 연달아 나오면 지루하니까 **같은 종류는 연속 2개까지**만 놓아요.
비슷한 옷(예: 칼라 옷)도 상위 10개 안에 **3개까지만** 넣어요.

### 4단계: 홈 화면 구성
쇼핑 앱 첫 화면처럼 칸을 나눠요.
"오늘의 추천 10개" → "상의 4개" → "하의 4개" → "아우터 4개" → "원피스 4개" → "추천 코디 3세트"

### 5단계: 코디 추천
상의와 하의를 모두 짝지어 보고, 두 옷 점수의 평균을 내요.
체형별로 **궁합이 좋은 조합이면 보너스 점수**를 줘요.
예: 웨이브는 "크롭 상의 + 하이웨이스트 바지"면 다리가 길어 보이니까 보너스 +0.10

### 6단계: 추천 이유 + 학습
- **이유**: 옷의 태그를 문장으로 바꿔요. → "칼라가 목선을 세워 주고, 몸에 맞는 핏이 라인을 정돈해 줘요."
- **학습**: 사용자가 옷을 클릭하면 조금, 찜하면 더, 사면 더 많이 그 옷의 태그를 "좋아함"으로 기억해요. 반품하면 "싫어함"으로 기억해요. 다음 추천부터 반영돼요.
- **재진단 안내**: 진단은 스트레이트인데 최근 찜·구매한 옷의 절반 이상이 스트레이트가 피해야 할 옷이라면, 진단이 틀렸을 수 있으니 "체형을 다시 진단해 볼까요?"라고 물어요.

### 7단계: 화면과 연결 (API)
위 기능을 웹 화면이 불러 쓸 수 있게 서버에 연결했어요.
화면이 "이 사람 체형은 스트레이트 80%야"라고 보내면, 서버가 홈 화면 목록·코디·이유를 돌려줘요.

## 제대로 만들었는지 어떻게 확인했나요?
**정답을 손으로 먼저 계산하고, 프로그램 결과가 같은지 자동으로 비교하는 테스트**를 만들었어요(총 34개).
예: "스트레이트에게 칼라 셔츠는 0.785점이어야 한다" → 프로그램도 0.785가 나오면 통과.
코드를 고칠 때마다 테스트를 돌려서 전에 되던 게 망가지지 않았는지 확인해요.

## 아직 남은 것과 한계
- **B 파트 코드로 교체**: 지금은 체형 적합도를 임시 코드로 계산해요. B 팀원 코드가 오면 한 줄만 바꾸면 돼요.
- **숫자는 임시값**: 60/25/15, +2/−3 같은 숫자는 근거 있는 출발점일 뿐, 실제 사용자 데이터로 다시 맞춰야 해요.
- **스타일 이론의 한계**: 골격진단은 통용되는 스타일링 이론이지 의학적으로 검증된 분류는 아니에요. 전문가 감수가 필요해요.
- **연습용 데이터**: 상품 30개와 태그는 시연용이에요. 실제 상품에는 태그를 붙이는 방법이 따로 필요해요.
- **기억은 임시**: 사용자 취향은 서버 메모리에만 저장돼서 서버를 끄면 사라져요. 실제 서비스라면 데이터베이스가 필요해요.

## 발표 때 예상 질문과 답
- **"점수 비중은 왜 60/25/15예요?"** → 서비스의 핵심이 체형 맞춤이라 체형에 가장 큰 비중을 줬고, 취향과 유행은 보조로 넣었어요. 실제 데이터를 모으면 조정할 임시값이에요.
- **"왜 피해야 할 옷을 단일형만 빼요?"** → 혼합형은 두 타입 특징을 다 가져서, 한 타입이 피해야 할 옷이 다른 타입에는 어울릴 수 있어요. 그래서 빼지 않고 점수만 낮춰요.
- **"같은 종류를 왜 섞어요?"** → 점수만 보면 상의만 잔뜩 나올 수 있어요. 다양하게 보여 줘야 사용자가 더 많이 둘러봐요.
- **"추천이 틀리면요?"** → 사용자 반응을 학습해서 점점 맞춰 가고, 반응이 진단과 계속 어긋나면 재진단을 권해요.
